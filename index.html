Bu rehber kime ve neye göre

Bu rehber, kod yazan ama GitHub kullanmamış sağlık ve epidemiyoloji araştırmacıları için yazıldı. Amaç GitHub’ı bir yazılımcı gibi değil, bir araştırmacı gibi kullanmanı sağlamak: analiz kodunu güvende tutmak, sürümlerini takip etmek, ekiple çalışmak ve sonuçları yayınlamak.

Rehber boyunca her iş için iki yol göstereceğiz:

  • 🟢 Kolay yol — tarayıcı ve GitHub Desktop (kod yazmadan, tıklayarak)
  • 🔵 İleri yol — terminal / komut satırı (Git komutlarıyla)

İkisini de bilmen gerekmez. Önce kolay yolla başla; terminale ihtiyaç duyduğunda ilgili bölüme dönersin.

İpucuNasıl okumalı?

Soldaki içindekiler menüsünden istediğin konuya atlayabilirsin. İlk kez kullanıyorsan sırayla “Git ve GitHub nedir?” → “Hesap oluşturma” → “GitHub Desktop” bölümlerini takip et.

1 Git ve GitHub nedir?

İkisi farklı şeylerdir ve bu ayrım kafa karışıklığının çoğunu çözer.

  • Git, bilgisayarındaki dosyaların değişikliklerini kaydeden bir sürüm kontrol sistemidir. “analiz_son.R”, “analiz_son_v2.R”, “analiz_GERÇEKTEN_son.R” dosyalarına son verir. Tek bir dosya tutarsın; Git onun tüm geçmişini hatırlar.
  • GitHub, Git ile takip edilen projelerin (depoların) saklandığı, paylaşıldığı ve birlikte çalışıldığı internet platformudur. Git’in bulutta yaşayan hali gibi düşün.

Benzetme: Git Word’ün “değişiklikleri izle” özelliği, GitHub ise dosyanın herkesin görüp katkı verebildiği Google Drive’daki hali gibidir.

1.1 Neden epidemiyoloji için önemli?

  • Yeniden üretilebilirlik (reproducibility): Bir analizin hangi kodla, hangi sürümde yapıldığı kayıt altındadır. Hakem “şu tabloyu nasıl ürettiniz?” dediğinde geçmişe dönebilirsin.
  • Yedek ve güvenlik: Bilgisayarın bozulsa bile kodun bulutta durur.
  • İş birliği: Aynı R/Python projesini birden fazla kişi, birbirinin üstüne yazmadan geliştirebilir.
  • Yayınlama: Quarto raporlarını, ders notlarını, paket dokümantasyonunu ücretsiz bir web sitesi olarak yayımlayabilirsin (bu rehberin kendisi de öyle yayımlanabilir).
UyarıHasta verisi uyarısı

GitHub’a kimliklendirilebilir hasta verisi, ham veri seti veya gizli bilgi yüklemeyin. GitHub kodu paylaşmak içindir, veriyi değil. Veriyi hariç tutmayı .gitignore bölümünde anlatıyoruz. Halka açık (public) depolarda her şey herkese görünür.

Rehber boyunca geçecek terimler. Şimdilik göz gezdir, ileride dönersin.

3 Hesap oluşturma

  1. https://github.com adresine git, Sign up’a tıkla.
  2. Bir e-posta, parola ve kullanıcı adı belirle.
    • Kullanıcı adın profil adresin olur: github.com/kullaniciadi. Akademik kimliğinin parçası olacağı için sade ve kalıcı bir ad seç (örn. aysenuryilmaz gibi).
  3. E-postanı doğrula. Ücretsiz plan araştırma için fazlasıyla yeterlidir.
İpucuAkademik avantajlar
  • GitHub Education / Student & Teacher programlarıyla bazı ücretli özellikler akademisyenlere ücretsiz açılabilir. Kurumsal e-postanla başvurmayı dene.
  • Profilini bir fotoğraf, kurum ve kısa biyografi ile doldur; yayınlarına atıf alırken bu profil görünürlüğünü artırır.

İki adımlı doğrulamayı (2FA) açman önerilir; GitHub bunu zaten birçok hesap için zorunlu tutmaktadır.

5 🟢 En kolay yol: GitHub web arayüzü

Hiçbir program kurmadan, sadece tarayıcıyla yapılabilecek işler.

5.1 Yeni depo (repository) oluşturma

  1. Sağ üstteki + → New repository.
  2. Repository name: proje adı (boşluk yerine tire kullan: kizamik-analizi).
  3. Description: kısa açıklama (isteğe bağlı).
  4. Public (herkese açık) ya da Private (sadece sen ve davet ettiklerin) seç.
  5. Add a README file kutusunu işaretle — deponun ilk sayfası hazır gelir.
  6. İstersen bir .gitignore şablonu (örn. R) ve bir lisans seç.
  7. Create repository.

5.2 Dosya yükleme (sürükle-bırak)

Depo sayfasında Add file → Upload files de, dosyalarını pencereye sürükle, alttaki kutuya kısa bir açıklama yaz ve Commit changes’e bas. Bu kadar.

Not

Web arayüzünden tek seferde çok büyük veya çok sayıda dosya yüklemek zordur. Düzenli çalışacaksan GitHub Desktop veya terminale geç.

5.3 Tarayıcıda dosya düzenleme

Bir dosyaya tıkla → sağ üstteki kalem (✏️) simgesine bas → düzenle → Commit changes. Küçük düzeltmeler (bir yazım hatası, README’ye bir satır) için en hızlı yöntem budur.

İpucu: Depo ana sayfasında klavyeden . (nokta) tuşuna basarsan, depo tarayıcı içinde tam bir VS Code düzenleyicisinde açılır (github.dev) — kurulum gerektirmez.

6 🟢 GitHub Desktop ile çalışma

Yeni başlayanlar için en rahat yol. Komut yazmadan, butonlarla commit / push / pull yaparsın.

6.1 Kurulum ve giriş

  1. https://desktop.github.com adresinden indir, kur.
  2. Aç → Sign in to GitHub.com → tarayıcıda hesabınla yetki ver. (Kimlik doğrulamayı program kendi halleder; parola/anahtar derdi yok.)
  3. Adını ve e-postanı sorarsa, GitHub hesabınla aynısını gir.

6.2 Temel iş akışı

a) Depoyu bilgisayarına alma (clone): File → Clone repository → listeden deponu seç → bilgisayarında bir klasör belirle → Clone.

b) Yeni depo oluşturma: File → New repository → ad, klasör, README seç → Create repository → sağdaki Publish repository ile GitHub’a yükle.

c) Değişiklik yapma ve kaydetme (commit): Dosyaları her zamanki programlarınla (RStudio, VS Code, Excel…) düzenle ve kaydet. GitHub Desktop’a dönünce Changes sekmesinde değişen dosyaları görürsün:

  1. Kaydetmek istediklerinin yanındaki kutuları işaretle.
  2. Sol altta Summary kutusuna kısa bir başlık yaz (örn. “Yaş standardizasyonu eklendi”).
  3. Commit to main’e bas.

d) GitHub’a gönderme (push): Üstteki Push origin düğmesine bas. Artık değişikliklerin bulutta.

e) Güncellemeleri alma (pull): Başka biri (veya başka bir bilgisayarın) değişiklik yaptıysa, çalışmaya başlamadan önce Fetch origin → Pull origin ile en güncel hali çek.

İpucuAltın kural

Çalışmaya başlamadan pull, işin bitince commit + push. Bu sıra çakışmaların çoğunu önler.

7 🔵 Terminal / komut satırı ile çalışma

Daha güçlü ve hızlı, ama biraz öğrenme gerektirir. R kullanıcıları çoğu işi RStudio’nun Git paneliyle de yapabilir (aynı komutların butonlu hali); yine de komutları bilmek işine yarar.

7.1 Git’i kurma

  • Windows: https://git-scm.com adresinden Git for Windows’u kur (kurulum sırasındaki varsayılanlar yeterli). Beraberinde Git Bash terminali gelir.
  • macOS: Terminale git --version yaz; kurulu değilse macOS kurmayı önerir. Alternatif: brew install git.
  • Linux: sudo apt install git (Debian/Ubuntu) ya da dağıtımının paket yöneticisi.

7.2 İlk kez bir defalık ayar

Commit’lere adının yazılması için kimliğini tanıt:

git config --global user.name "Ayşe Yılmaz"
git config --global user.email "ayse@ornek.edu.tr"

7.3 Kimlik doğrulama (önemli!)

GitHub artık terminalden parola kabul etmiyor. İki yaygın yol var:

  • Yöntem 1: GitHub CLI (en kolay)
  • Yöntem 2: SSH anahtarı

GitHub CLI aracını kur, sonra:

gh auth login

Sorulara tarayıcıdan yanıt ver; gerisini kendisi halleder. Sonraki tüm push/pull işlemleri sorunsuz çalışır.

Bir defa kur, bir daha uğraşma:

# 1) Anahtar üret (e-postanı yaz)
ssh-keygen -t ed25519 -C "ayse@ornek.edu.tr"
# Enter'lara bas (varsayılan konum ve boş parola olur)

# 2) Açık anahtarı ekrana yazdır ve kopyala
cat ~/.ssh/id_ed25519.pub

Kopyaladığın metni GitHub’da Settings → SSH and GPG keys → New SSH key altına yapıştır. Artık depoları git@github.com:... (SSH) adresiyle klonlayabilirsin.

Not

En kolayı: kimlik doğrulamayı dert etmek istemiyorsan GitHub Desktop veya GitHub CLI kullan; ikisi de bu işi senin yerine yapar.

7.4 Günlük kullanılan komutlar

# Bir depoyu indir (klonla)
git clone https://github.com/kullanici/proje.git

# Klasöre gir
cd proje

# Neyin değiştiğini gör
git status

# Değişiklikleri hazırla (stage)
git add analiz.R            # tek dosya
git add .                   # tüm değişiklikler

# Kaydet (commit) — mesaj yaz
git commit -m "Yaş standardizasyonu eklendi"

# GitHub'a gönder
git push

# GitHub'dan güncellemeleri al
git pull

# Geçmişi gör
git log --oneline

Tipik bir günün özeti:

git pull                       # güne güncel başla
# ... RStudio'da çalış, dosyaları kaydet ...
git add .
git commit -m "Tabloları güncelledim"
git push                       # günü buluta yazarak bitir

7.5 Dallarla (branch) çalışmak

Ana hattı (main) bozmadan deneme yapmak için:

git switch -c yeni-analiz       # yeni dal aç ve geç
# ... çalış, commit'le ...
git switch main                 # ana dala dön
git merge yeni-analiz           # denemeni ana dala kat

7.6 Sıfırdan yeni depo (yereldeki klasörü GitHub’a bağlama)

cd mevcut-projem
git init
git add .
git commit -m "İlk commit"
# GitHub'da boş bir depo açtıktan sonra adresini bağla:
git remote add origin git@github.com:kullanici/projem.git
git push -u origin main

7.7 .gitignore: istenmeyen dosyaları hariç tutmak

Bazı dosyalar asla GitHub’a gitmemeli: hasta verisi, devasa çıktı dosyaları, geçici dosyalar. Depo köküne .gitignore adlı bir dosya koy ve içine kalıpları yaz:

.gitignore
# Veri klasörünün tamamı (HASTA VERİSİ!)
data/
*.csv
*.xlsx
*.dta
*.sav

# R/RStudio geçici dosyaları
.Rhistory
.RData
.Rproj.user/

# Çıktılar
*.html
/_site/
/docs/

# İşletim sistemi çöpleri
.DS_Store
Thumbs.db
Uyarı

.gitignore, dosyayı henüz hiç commit etmediysen çalışır. Bir veri dosyasını yanlışlıkla yükledikten sonra silmek yetmez — geçmişten temizlemek gerekir (git rm --cached dosya + commit, gerekirse geçmiş temizliği). Bu yüzden .gitignore’u en baştan ayarla.

8 README sayfalarını süslemek

README.md, deponun vitrinidir; biri deponu açtığında ilk gördüğü şeydir. Markdown denen sade biçimlendirme diliyle yazılır (Quarto’da kullandığının aynısı).

8.1 Markdown’ın temelleri

# Büyük başlık (H1)
## Alt başlık (H2)
### Daha alt başlık (H3)

Normal metin. **Kalın**, *italik*, `kod parçası`.

  - Alt madde

2. Liste

> Alıntı kutusu

Rozetler README’ye renkli küçük etiketler ekler. https://shields.io adresinden üretebilirsin. Örnekler:

8.5 İçindekiler, emoji ve görseller

  • Uzun README’lerde başlıklara bağlantı vererek elle bir içindekiler listesi yapabilirsin.
  • Emoji’leri doğrudan yapıştırabilir ya da :rocket: 🚀, :warning: ⚠️ gibi kısa kodlarla yazabilirsin.
  • Görselleri depo içinde bir img/ klasörüne koyup ![](img/akis-semasi.png) ile gömmek en sağlam yoldur.

8.6 İyi bir araştırma README’sinde ne olmalı?

  1. Projenin adı ve tek cümlelik amacı
  2. İçerik: hangi klasörde ne var (kısa bir dosya haritası)
  3. Nasıl çalıştırılır: gereken paketler, çalıştırma sırası
  4. Veri notu: verinin nereden geldiği / neden depoda olmadığı
  5. Atıf: çalışmaya nasıl atıf verilmeli
  6. Lisans ve iletişim
İpucu

Düzenlerken GitHub’daki dosya görünümünde Preview sekmesiyle nasıl göründüğünü canlı kontrol edebilirsin.

9 Issue (konu) açmak

Issue, bir depo hakkında konuşma açtığın yerdir: hata bildirimi, soru, yapılacaklar listesi ya da öneri. Hem kendi projende hem başkasınınkinde kullanılır.

9.1 Nasıl açılır?

  1. Deponun üstündeki Issues sekmesine git → New issue.
  2. Kısa ama net bir başlık yaz (örn. “Yaş gruplaması 85+ için hatalı”).
  3. Açıklamaya şunları ekle:
    • Ne bekliyordun, ne oldu
    • Nasıl tekrar üretilir (mümkünse küçük bir kod parçası)
    • Sürüm bilgisi (R sürümü, paket sürümü)
  4. Submit new issue.

9.2 İşini kolaylaştıran özellikler

  • Labels (etiketler): hata, iyileştirme, soru gibi renkli sınıflandırmalar.

  • Assignees: issue’yu birine ata.

  • @kullanıcı yazarak birine haber ver; #12 yazarak başka bir issue’ya bağlan.

  • Onay kutulu yapılacaklar listesi:

    - [x] Veri temizliği
- [ ] Yaş standardizasyonu
- [ ] Tabloların kontrolü

  • Bir commit mesajına Fixes #14 yazarsan, o commit GitHub’a ulaştığında 14 numaralı issue otomatik kapanır.

Not

Tek başına çalışsan bile issue’lar mükemmel bir yapılacaklar / fikir defteridir. Aklına geleni issue olarak açıp sonra kapatabilirsin.

10 Katkı sağlamak (contribute)

Başkasının projesini geliştirmenin standart yolu fork → değişiklik → pull request akışıdır. Çünkü genelde başkasının deposuna doğrudan yazma yetkin olmaz.

10.1 Adım adım (kolay yol — tarayıcı + Desktop)

  1. Fork: Katkı vereceğin deponun sağ üstündeki Fork düğmesine bas. Artık o deponun kendi hesabında bir kopyası var.
  2. Clone: Kendi kopyanı GitHub Desktop ile bilgisayarına al.
  3. Branch: Değişiklik için yeni bir dal aç (örn. tablo-duzeltme).
  4. Değişiklik + commit + push: Düzeltmeni yap, commit’le, kendi forkuna push’la.
  5. Pull Request (PR): GitHub’da forkunun sayfasında çıkan Compare & pull request düğmesine bas. Ne değiştirdiğini açıkla ve Create pull request de.
  6. Proje sahibi PR’ını inceler, yorum yapar, kabul ederse merge eder.

10.2 Aynı işin terminaldeki hali

# Forkunu klonladıktan sonra
git switch -c tablo-duzeltme
# ... düzelt ...
git add .
git commit -m "Tablo başlıkları düzeltildi"
git push -u origin tablo-duzeltme
# Ardından GitHub'daki bağlantıdan PR aç
İpucuKatkı görgü kuralları
  • Önce projenin CONTRIBUTING.md dosyasına ve açık issue’lara bak.
  • Büyük bir değişiklikten önce bir issue açıp niyetini belirt; emek harcamadan önce sahibinin onayını al.
  • Bir PR’da tek bir konuya odaklan; incelemesi kolay olur.

11 Web sitesi yayınlamak (GitHub Pages + Quarto)

GitHub, depolarını ücretsiz bir web sitesine çevirebilir: GitHub Pages. Quarto kullandığın için en pratik yolu Quarto üzerinden anlatıyoruz — bu rehber de tam olarak böyle yayımlanabilir.

11.1 Yol A — Quarto ile (önerilen)

Quarto’nun yerleşik komutu çoğu işi otomatik yapar. quarto publish gh-pages komutu ilk çalıştırıldığında, yoksa hem yerelde hem uzakta bir gh-pages dalını otomatik oluşturur.

1) Çıktıları Git’in dışında tut. Quarto sitesi _site/ (veya kitap için _book/) klasörüne render edilir; bunları depoya koymaya gerek yok. Depo köküne bir .gitignore ekle:

.gitignore
/.quarto/
/_site/

2) Yayımla. Proje klasöründe, gh-pages dalında olmadığından emin olarak şu komutu çalıştır:

quarto publish gh-pages

Bu konfigürasyon değişikliğinden sonra GitHub sitenin dağıtımını tetikler; ayrıca main dalına her commit ve push yaptığında siten güncellenir.

3) Sonuç. Proje siteleri (https://kullanici.github.io/depo/) için GitHub yeni dalı algılar ve Pages’i gh-pages dalından yayımlayacak şekilde kendisi yapılandırır; Settings : Pages altında elle bir ayar gerekmez.

NotKullanıcı/kurum sitesi farkı

Kullanıcı ve kurum siteleri (https://kullanici.github.io/ adresinde sunulanlar) GitHub tarafında farklı davranır: varsayılan yayın kaynakları gh-pages değil main dalıdır. Bu durumda ilk quarto publish gh-pages çalıştırmasından sonra Settings : Pages altında kaynak dalı elle gh-pages olarak değiştirmen gerekir; Quarto bu durumu algıladığında ilgili ayar sayfasına doğrudan bir bağlantı içeren bir uyarı yazdırır.

11.1.1 Otomatik yayın (GitHub Actions) — isteğe bağlı

Her seferinde komut çalıştırmak istemezsen, depoya bir GitHub Actions iş akışı ekleyip her push’ta sitenin otomatik yeniden derlenmesini sağlayabilirsin. Önce bir kez quarto publish gh-pages çalıştırıp dalı oluşturman, sonra .github/workflows/publish.yml eklemen önerilir. Ayrıntılar için Quarto belgeleri: https://quarto.org/docs/publishing/github-pages.html.

11.2 Yol B — Quarto’suz, düz HTML/Markdown

Elinde hazır bir index.html veya Markdown sayfaları varsa:

  1. Depo → Settings → Pages.
  2. Source olarak bir dal (örn. main) ve klasör seç: / (root) ya da /docs.
  3. Kaydet. Birkaç dakika içinde https://kullanici.github.io/depo/ adresinde yayında olur.

Jekyll işlemesini istemiyorsan depo köküne boş bir .nojekyll dosyası ekle.

İpucu

Yayınlanan adresi her zaman Settings → Pages sayfasının en üstünde görebilirsin. İlk yayında birkaç dakika gecikme normaldir.

12 Repo yönetimi

Deponu derli toplu ve güvenli tutmak için.

12.1 İşbirlikçi (collaborator) ekleme

Özel bir depoda başkalarının da yazabilmesi için: Settings → Collaborators → Add people → kullanıcı adıyla davet et. Açık (public) depoda herkes görebilir ama yazmak için yine davet/PR gerekir.

12.2 Dalları koruma (branch protection)

Ekip büyüdükçe main dalını koruyabilirsin: Settings → Branches altında “doğrudan push’u engelle, değişiklikler PR ile gelsin ve onaylansın” gibi kurallar tanımlanır. Bu, ana analizin yanlışlıkla bozulmasını önler.

12.3 Sürümler (releases) ve etiketler

Bir makaleyi gönderdiğinde veya analizi “dondurduğunda” o anı bir release olarak işaretle: depo sağ taraftaki Releases → Create a new release → bir etiket (örn. v1.0) ve not. Böylece “makalede kullanılan tam sürüm” her zaman bulunur.

İpucuZenodo ile DOI

GitHub deposunu Zenodo’ya bağlayıp bir release yayımladığında, çalışmana atıf verilebilir bir DOI atanır. Bu, kodunu makalende kaynak gösterebilmen için çok kullanışlıdır.

12.4 Lisans eklemek

Lisanssız kod, başkalarının yasal olarak kullanamayacağı koddur. Add file → Create new file → LICENSE yazınca GitHub sana hazır şablonlar sunar. Yaygın seçenekler:

  • MIT — çok serbest, basit.
  • GPL-3.0 — türev çalışmaların da açık kalmasını ister.
  • CC-BY-4.0 — kod değil de veri/doküman için daha uygundur.

13 Sık karşılaşılan sorunlar (SSS)

“Push reddedildi / updates were rejected” hatası alıyorum. Muhtemelen GitHub’da senin bilgisayarında olmayan değişiklikler var. Önce git pull (veya Desktop’ta Pull origin), sonra tekrar push’la.

Merge conflict (birleştirme çakışması) çıktı. İki kişi aynı satırı değiştirdiğinde olur. Git, dosyaya <<<<<<<, =======, >>>>>>> işaretleri koyar. İstediğin hali bırakıp bu işaretleri silersin, sonra commit’lersin. RStudio ve VS Code bunu görsel olarak kolaylaştırır.

Yanlışlıkla hasta verisi/büyük dosya yükledim. .gitignore’a ekleyip git rm --cached dosya ile takibi durdur, commit’le. Dosya geçmişte kaldıysa tamamen temizlemek için ek araçlar gerekir (git filter-repo gibi) — bu durumda yardım iste, çünkü geçmiş yeniden yazılır.

Son commit mesajımı yanlış yazdım. Henüz push’lamadıysan: git commit --amend -m "Doğru mesaj".

Bir dosyayı son commit’teki haline geri almak istiyorum. git restore dosya.R (henüz commit edilmemiş değişiklikleri siler — dikkat).

Hesabımda iki bilgisayar var, hangisi güncel? Her zaman GitHub’daki kopya gerçeğin kaynağıdır. Çalışmaya başlamadan pull, bitince push alışkanlığı bu karışıklığı bitirir.
